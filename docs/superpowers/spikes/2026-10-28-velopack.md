# Spike: distributing the desktop apps with Velopack

Issue: corundum-framework#51. The question: can [Velopack](https://docs.velopack.io/)
(the `velopack` crate and `vpk`, 1.2.161) install, update and uninstall a corundum app on
Windows, macOS and Linux, and what does it leave to us? The answers decide the designs of
#51's packaging (CI, signing) and runtime (updates, hooks, launcher, services) parts.

The demo carries the probe, behind its `velopack` feature (`demo/src/velopack.rs`), and
`.github/workflows/demo-release.yml` packages it on a `demo-v<x.y.z>` tag.

## Found in the sources (2026-10-28)

Read from the crate (1.2.161) and the `velopack/velopack` repository (`develop`).

1. **The install, update and uninstall hooks are Windows only.** In the crate the
   `on_after_install_fast_callback`, `on_after_update_fast_callback`,
   `on_before_update_fast_callback` and `on_before_uninstall_fast_callback` builders are
   `#[cfg(target_os = "windows")]`. On the updater's side the hooks are run only in
   `apply_windows_impl.rs` and `uninstall.rs` (Windows); `apply_osx_impl.rs` and
   `apply_linux_impl.rs` take the hook mode and ignore it (`_hook_mode`). The docs' "hooks
   run on every OS" is wrong for 1.2.161.
   - On macOS and Linux an app learns of an install or an update only at its own next
     start: `VELOPACK_FIRSTRUN`, `VELOPACK_RESTART`, or comparing the package version
     with one it kept (what the demo's `velopack-seen-version` does).
   - **Nothing runs on uninstall on macOS or Linux**: the user deletes the `.app` or the
     AppImage. Whatever the app registered (a LaunchAgent, a systemd unit, a symlink on
     `PATH`, a launcher entry) stays behind, pointing at nothing.
2. **The macOS `.pkg` passes `VELOPACK_FIRSTRUN` through `open`.** Its postinstall script
   runs `sudo -u "$USER" env VELOPACK_FIRSTRUN=1 open "$2/<bundle>/"`. The guess that
   LaunchServices would drop the variable was wrong: on a clean Mac it arrived (below).
3. **`GithubSource` reads only the repository's 10 newest releases** (`per_page=10`), and
   merges the `releases.<channel>.json` of each that has one. In a repository that tags
   library releases too (sapphire-framework, the apps' `core-v`, `mcp-v`…), an app's
   releases fall out of those 10.
4. **An update check does not look at the package id.** The feed is chosen by channel
   alone (`releases.<channel>.json`). Two apps released from one repository (asteria's
   photos and music) would read each other's packages unless their channels differ.
5. **`apply_updates_and_restart` exits the process** (`exit(0)` after starting the
   updater), so the app must save what it holds before calling it.
6. **vpk is a .NET tool** (`dotnet tool install -g vpk`, .NET 8 SDK), released with the
   crate under the same version.
7. **Linux gets an AppImage only**; `vpk pack` on Linux has no option for a `.desktop`
   entry beyond `--categories`.

## Findings on the machines

### Windows (2026-10-28, demo-v0.0.1 → 0.0.2)

From the demo's `velopack.log`:

- **Install**: `Setup.exe` installed to `%LocalAppData%\corundum-framework-demo\current\`
  and ran `--veloapp-install 0.0.1`, then started the app with `VELOPACK_FIRSTRUN=true`
  (`hook first-run`). The demo's own version check saw a first start as well.
- **Update** with the daemon running from `current\`: one second from Apply to the new
  version's start, in this order: the old version's `--veloapp-obsolete 0.0.1`, the new
  one's `--veloapp-updated 0.0.2`, then a start with `VELOPACK_RESTART=true`
  (`hook restarted`). The demo's version check saw `0.0.1 -> 0.0.2` too.
- **Paths are stable**: before and after the update the app and the daemon ran from the
  same `...\current\` path. A service or `PATH` entry can point there.
- **A running daemon did not stop the update.** The updater presumably killed it with the
  rest of `current\`; the log cannot say, as the demo that would have logged its exit had
  quit first.
- **Uninstall** ran `--veloapp-uninstall 0.0.2`.

### macOS (2026-10-28, first try: not clean)

The first try ran where an earlier `cargo install` had left the launcher's own
`~/Applications/Corundum Demo.app` (a link to `~/.cargo/bin/corundum-framework-demo`).
`vpk pack --packTitle "Corundum Demo"` names Velopack's bundle the same, and the package
went to `~/Applications/Corundum Demo.localized/Corundum Demo.app`. After the update the
daemon's executable was missing from that bundle (`No such file or directory`), although
the 0.0.2 package holds it. To repeat on a clean machine before drawing anything from it.

What the try did show: **the launcher and Velopack must not both make a bundle under one
name.** A Velopack build has a real `.app`; the launcher's generated one only collides with
it. (`VELOPACK_FIRSTRUN` was missing on this try too; on the clean one it arrived.)

### macOS (2026-10-28, clean)

After removing the earlier bundle, the binaries under `~/.cargo/bin` and `~/.local/bin`,
Velopack's cache and the demo's log:

- **Install**: the `.pkg` put the bundle in `~/Applications/Corundum Demo.app` and started
  it with `VELOPACK_FIRSTRUN=1` (`hook first-run`).
- **Update**: Apply to the new version's start in one second, with
  `VELOPACK_RESTART=true` (`hook restarted`); no other hook, as the sources say. The path
  stayed `~/Applications/Corundum Demo.app/Contents/MacOS/`, and the new bundle has the
  daemon (its absence on the first try came from the collision).
- **A running daemon survives the update.** The daemon started from 0.0.1 kept running
  after the bundle was swapped for 0.0.2's (it holds the old, deleted files), beside the
  one started from 0.0.2. Unlike Windows, the updater stops nothing but the app.
- **It survives the uninstall too.** Moving the `.app` to the Bin left both daemons
  running; nothing was left in `~/Applications`.
- **Nothing starts the daemon again** after an update: Velopack restarts the main app
  only. Starting at login and after an update is the app's to arrange (#51 part 5).
