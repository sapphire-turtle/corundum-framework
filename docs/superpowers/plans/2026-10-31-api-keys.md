# API Keys Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new `corundum-framework-keys` crate (key store, verifier, axum layer, clap subcommand) and a `KeysPage` in `corundum-framework-gui`, so sapphire-framework and asteria share one API-key implementation.

**Architecture:** `KeyStore` is a directory of one TOML file per key, chosen by the app; it reads every `*.toml`, groups records by `id`, and treats `<id>.toml` as the key and other files as sync conflict copies. `KeyVerifier` caches successes and reloads the store on a miss. The GUI page draws whatever a `KeysBackend` answers; `LocalKeys` is the backend over a `KeyStore`.

**Tech Stack:** Rust 2024, serde + toml, chrono, uuid (v7), blake3, sha2, getrandom, base64, subtle-free constant-time compare (fold over bytes), axum 0.8 (feature), clap 4 (feature), egui 0.37.

**Spec:** `docs/superpowers/specs/2026-10-31-api-keys-design.md`

## Global Constraints

- New crate `crates/corundum-framework-keys`, version `0.4.0` with `version_group = "corundum"` (release-plz moves it with the others); features `axum` and `clap`, both off by default.
- The page lives in `corundum-framework-gui` behind feature `keys` (depends on `corundum-framework-keys` with `serde` available).
- Hash strings on disk: `"blake3:<64 hex>"` for keys made here; `"sha256:<64 hex>"` accepted. Nothing else is accepted.
- Token: optional app prefix + 32 random bytes as base64url without padding; the hash covers the whole token, prefix included. Shown once.
- New ids: UUIDv7 simple form (32 lowercase hex). Ids are ASCII letters, digits, `-`, `_` only.
- Default cache TTL: 30 s.
- Strings: `en` and `ja`, ids `corundum-keys-*`, in `crates/corundum-framework-gui/locales/{en,ja}/corundum.ftl`.
- Never log or `Debug`-print a token.

## Review Focus

- Two records with the same `id` where neither file is `<id>.toml` (only conflict copies survive, e.g. the primary was deleted by hand): no key exists, so the token is refused and `list` does not show it.
- A store directory that is unreadable or missing after `open` (workspace moved): `KeyVerifier::verify` refuses rather than panics.
- A presented token with surrounding whitespace or an empty bearer value: refused (401), never matched against an empty hash.
- A temp file left by a crashed write (`.<id>.toml.tmp`): ignored by reading, not taken for a record.
- Concurrent `add` of the same name through two `KeyStore`s on one directory: both succeed on disk, and `resolve(name)` answers `Ambiguous`.
