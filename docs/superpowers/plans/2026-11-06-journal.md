# Journal (undo log) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `corundum-framework-journal`: a log that runs batches of app-defined
operations and records them, and undoes or redoes them with compensating batches. Undo
works per UI session, inside an undo window. The store is `MemoryStore`.

**Architecture:**
- **Operations**: an app implements `Operation<C>` with typed `Plan` and `Done`, and
  registers it in a `Registry<C>`. The registry erases the types to JSON, which is what
  the records hold.
- **The writer**: `Journal<C>` owns one worker thread that runs queued jobs one at a time.
  The job kinds are:
  - a batch of plans;
  - a compensation of a target batch, its plans built from the target's records when the
    job runs.
- **What happens on the caller's thread**: under one mutex, and synchronously:
  - `submit` writes the batch's `BatchBegin`;
  - `undo` / `redo` / `undo_batch` choose and check their target, and reserve it.

  So errors come back at once, and two quick Ctrl+Z take two different batches.
- **The store**: `JournalStore` keeps records and summaries. `MemoryStore` drops its
  oldest batches beyond its capacity.

**Tech Stack:** Rust 2024 (toolchain 1.99.0), serde / serde_json, grain-id 0.15 (`serde`),
thiserror 2, tracing.

**Spec:** `docs/superpowers/specs/2026-11-06-workspace-fs-journal-design.md`, section
"`corundum-framework-journal`". This plan is its "Order of work" step 2, on the branch
`journal`, stacked on `workspace-fs-journal` (PR #132). `JsonlStore` is step 5, not here.

## Global Constraints

- **Crate:**
  - `corundum-framework-journal`, version `0.11.0`, `MIT OR Apache-2.0`, in release-plz's
    `version_group = "corundum"`.
  - Dependencies: serde, serde_json, `grain-id = { version = "0.15", features = ["serde"] }`,
    thiserror, tracing.
  - No tokio and no file system. `#![warn(missing_docs)]`.
- **Wire names** (snake_case):
  - `Skip` has the reasons `precondition_failed`, `exists`, `not_found`, `invalid_path`,
    `denied`, `io` (with a message), `unknown_kind`, `not_undoable`.
  - Added here: `invalid_plan` (with a message), for a child plan that does not parse. That
    is an app's bug; an operation submitted by a client with a bad plan rejects the whole
    `submit` instead.
- **Defaults:**
  - `UndoPolicy { max_batches: 20, max_age: 1 hour }`.
  - The worker's queue holds 64 jobs; beyond that, `Busy`.
  - `MemoryStore::default()` keeps 200 batches.
- **Deviations from the spec**, decided here:
  - **The window's count is per origin.** `max_batches` counts the batches of the target's
    own origin. Counted over the whole journal, an agent making 20 batches would expire the
    person's Ctrl+Z, against the spec's goal that Ctrl+Z is the UI's own.
  - **`MemoryStore` keeps 200 batches by default**, not "twice `max_batches`": with the
    count per origin, two origins already need more than 40.
- **Time:** `at` is milliseconds since the Unix epoch, as `i64`. The clock is
  `JournalConfig::now`, so tests can move it.
- **Compensating batches run no children.** The children an inverse's `apply` returns are
  dropped, because the original children have their own inverses in the batch already.
  Running them would move a sidecar twice. The spec says nothing on this; it is decided
  here.
- **Undo builds its plans from operations that were done.** Skipped operations are left
  out.
  - A kind this build does not know is recorded as `Skipped(unknown_kind)`, with
    `plan: null`.
  - An operation whose `inverse` is `None` is recorded as `Skipped(not_undoable)`.
- **A panic in `check` or `apply`** is caught (`catch_unwind`). The operation is
  `Skipped(io: "the operation panicked")`, and the worker lives on.
- **Gate:** `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --check`
  stay clean.

## Review Focus

1. **Two Ctrl+Z pressed quickly**, the second while the first's compensation is still
   queued: the second undoes the next older batch, with no `already_undone`.
   → `two_quick_undos_take_two_batches` (Task 5).
2. **Ctrl+Z right after `submit`**, while the batch is still running: the undo waits behind
   it, and compensates every operation it did.
   → `undo_right_after_submit_waits_for_the_batch` (Task 5).
3. **An operation that panics**: it is skipped, the batch goes on, and later batches still
   run. → `a_panicking_op_is_skipped_and_the_worker_survives` (Task 4).
4. **An agent's flood**: 25 batches from an agent's origin after the person's one leave the
   person's Ctrl+Z working. → `another_origins_batches_do_not_expire_mine` (Task 5).
5. **The children of an inverse in a compensating batch**: they do not run.
   → `children_do_not_run_in_a_compensating_batch` (Task 5).

### Task 4: `Journal`: running batches

**Files:**
- Create: `crates/corundum-framework-journal/src/journal.rs`, `src/error.rs`,
  `tests/common/mod.rs`, `tests/run.rs`

**Interfaces:**
- Consumes: `Registry` (Task 2), `JournalStore` and `MemoryStore` (Task 3), and the records
  (Task 1).
- **Produces: the configuration.**
  ```rust
  pub struct UndoPolicy { pub max_batches: usize, pub max_age: Duration }
  impl Default for UndoPolicy  // 20, one hour
  pub struct JournalConfig {
      pub policy: UndoPolicy,
      pub may_undo: Arc<dyn Fn(&Actor, &BatchBegin) -> bool + Send + Sync>, // default: principal equal
      pub now: Arc<dyn Fn() -> i64 + Send + Sync>,                          // default: SystemTime, ms
      pub queue: usize,                                                     // default: 64
  }
  impl Default for JournalConfig
  ```
- **Produces: `JournalError`** (`thiserror`), with the variants:
  - `NothingToUndo`, `NothingToRedo`
  - `AlreadyUndone(BatchId)`, `Expired(BatchId)`, `Forbidden(BatchId)`, `NotFound(BatchId)`
  - `Busy`
  - `UnknownKind { index: usize, kind: String }`, `InvalidPlan { index: usize, message: String }`
  - `Store(#[from] StoreError)`
- **Produces: `Journal<C: Send + Sync + 'static>`**, which is `Clone` (an `Arc` inside):
  - `Journal::new(registry: Registry<C>, ctx: C, store: impl JournalStore + 'static, config: JournalConfig) -> Journal<C>`
    starts the worker thread. The thread ends when the last handle is dropped.
  - `submit(&self, ops: Vec<Planned>, origin: &Origin, actor: &Actor, label: Option<String>) -> Result<BatchId, JournalError>`:
    - checks every op's kind and plan first, and rejects the whole batch with
      `UnknownKind` / `InvalidPlan` (at the first bad index) before writing anything;
    - then, under the state lock, queues the job with `try_send` and only if that worked
      appends the `BatchBegin`. The worker appends only under the same lock, so the begin
      is always first, and a refused batch leaves no trace;
    - answers `Busy` when the queue is full.
  - `status(&self, id) -> Result<BatchRecords, JournalError>`: `NotFound` when the store
    has no such batch. It is also the spec's `batch(batch_id)`.
  - `wait(&self, id) -> Result<BatchRecords, JournalError>`: blocks on a `Condvar` until
    the batch is `complete`.
  - `dry_run(&self, ops: &[Planned]) -> Result<Vec<Result<(), Skip>>, JournalError>`: the
    same up-front check as `submit`, then each `check`, on the caller's thread.
  - `history(&self, cursor: Option<BatchId>, limit: usize) -> Result<Vec<BatchSummary>, JournalError>`
- **The worker** runs a batch's ops in order. For each op:
  1. It calls `apply` outside the lock.
  2. It appends an `OpRecord` with a fresh `OpId`.
  3. On `Done`, it runs that op's children right after it, depth first, each with
     `parent: Some(op_id)`. A child's `Unparsed` becomes `Skipped(UnknownKind)` or
     `Skipped(InvalidPlan(m))`. A skipped op's children do not run.

  Then it appends `BatchEnd`, with `interrupted: false`.

- **Test fixtures** (`tests/common/mod.rs`), over a context
  `Ctx { values: Mutex<BTreeMap<String, i64>>, gate: Mutex<Option<mpsc::Receiver<()>>> }`:
  - `Set { key, to, expect: Option<i64> }`:
    - skips `PreconditionFailed` when `expect` differs from the current value;
    - its `Done` is `{ key, from: Option<i64>, to }`;
    - its inverse is `Set { key, to: from (or remove when None), expect: Some(to) }`.
  - `WithChild { key }`: sets `key` to 1, and has the child `Set { key: "{key}.side", to: 1 }`.
  - `Boom`: panics.
  - `Wait`: blocks on the gate's receiver.
  - `journal() -> (Journal<Ctx>, Arc<..>)`, with all the kinds registered.

### Task 5: Undo, redo and the undo window

**Files:**
- Create: `crates/corundum-framework-journal/src/undo.rs` (choosing and checking targets,
  and building a compensation's plans), `tests/undo.rs`
- Modify: `crates/corundum-framework-journal/src/journal.rs`

**Interfaces:**
- Consumes: `Journal`, its state, `JournalConfig` and the fixtures (Task 4).
- **Produces:**
  - `undo(&self, origin: &Origin, actor: &Actor) -> Result<BatchId, JournalError>`
  - `redo(&self, origin: &Origin, actor: &Actor) -> Result<BatchId, JournalError>`
  - `undo_batch(&self, target: BatchId, origin: &Origin, actor: &Actor) -> Result<BatchId, JournalError>`
  - Each returns the compensating batch's id; `wait` works on it.
- **The rules:**
  - **Stacks per origin:**
    - `submit` pushes onto the undo stack and clears the redo stack.
    - `undo` pops the undo stack and pushes the new compensation onto the redo stack.
    - `redo` pops the redo stack and pushes its new batch onto the undo stack.
    - `undo_batch` touches no stack.
    - While popping, entries that are already undone or reserved are dropped.
    - An empty stack is `NothingToUndo` / `NothingToRedo`.
  - **Checks on the target, in this order:**
    1. Missing from the store: `Expired` from a stack, `NotFound` from `undo_batch`.
    2. Already undone or reserved: `AlreadyUndone`.
    3. `may_undo` is false: `Forbidden`.
    4. `now - at > max_age`, or not among the newest `max_batches` batches of its own
       origin: `Expired`.

    A refused target stays on its stack.
  - **The compensating batch:**
    - It is a `BatchBegin` with the caller's origin and actor and the target's label.
    - It gets `redo_of = target` if the target is a compensation for an undo
      (`undo_of.is_some()`), and `undo_of = target` otherwise.
    - It is written and its target reserved, under the lock, before the job is queued.
  - **When the worker runs a compensation:**
    - It reads the target's records and takes the `Done` ops in reverse record order.
    - For each, it gets `inverse` from the registry. An unknown kind is recorded as
      `Skipped(UnknownKind)` with `plan: null`; `None` is recorded as
      `Skipped(NotUndoable)`.
    - It applies the inverse, drops its children, and records it.
    - The reservation is cleared after its `BatchEnd`.

- [ ] **Step 1: Write the failing tests** (`tests/undo.rs`)
  - `undo_puts_values_back`:
    - Submit `[Set a=1, Set b=2]`, then `undo`, then `wait` on the compensation.
    - `a` and `b` are gone again.
    - The compensation's begin has `undo_of == Some(first)`, and the first batch has
      `undone_by == Some(compensation)`.
  - `undo_reverses_children_first`:
    - Undo a `WithChild`.
    - The compensation's first record is the child's inverse (key `x.side`), then the
      parent's.
